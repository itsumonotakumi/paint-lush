# ペイントラッシュ！ 概要設計書

Nov 5, 2026 · @いつもの匠

要件定義書（ペイントラッシュ！ 要件定義書）のMVP範囲を、静的サイトで動くTypeScript＋Three.js構成に落とし込む。実装には入らない。

## 1. 設計方針と全体構成

全体を「プラットフォーム層／エンジン層／ゲーム層／表示層」の4層に分け、ゲームのロジックがブラウザAPIに直接触れないようにする。端末ごとの違い（入力・音声・画質）はエンジン層で吸収する。

&#91;embedded content: レイヤー構成 · 4層\]

上の層は下の層だけを呼び出す。ゲーム層の中心は塗りを管理するPaintSystemで、キャラの速度・CPUの判断・勝敗判定がすべてここの塗りグリッドを参照する。

**設計方針**

1. **固定タイムステップ**：ゲームの更新は毎秒60回の固定間隔で行い、描画とは切り離す。端末の性能差でゲームの速度が変わらないようにするためだ
2. **入力の抽象化**：キーボード・マウス・ゲームパッド・タッチ・ジャイロの入力を、すべて「移動」「射撃」「染遁」などのアクションに変換してからゲーム層へ渡す
3. **データ駆動**：武器・ステージ・CPUの強さ・音声の一覧はJSONで定義する。数値調整でコードを触らずに済むようにする
4. **塗りはGPUで描き、判定はCPUで持つ**：見た目の塗りはGPUのテクスチャに描く。足元判定と面積集計は、CPU側に持つ低解像度の塗りグリッドで行う。スマホでGPUからデータを読み戻すと重いため、それを避ける
5. **作り込みすぎない**：オンライン対戦は初版の対象外なので、通信同期のための仕組みは入れない。ただし乱数はシード付きにして、試合の再現テストをしやすくする

**各層の役割**

| 層 | 役割 | 主なモジュール |
| --- | --- | --- |
| 表示層 | 画面の切り替え、メニュー、HUD、タッチボタン | SceneManager、Screens、HUD、TouchControls |
| ゲーム層 | 試合の進行と全ルール | Match、Player、Weapon、PaintSystem、AI、Physics |
| エンジン層 | 端末差を吸収する共通基盤 | GameLoop、Renderer、InputManager、AudioManager、AssetLoader、SaveStore |
| プラットフォーム層 | ブラウザが提供するAPI | WebGL2、Web Audio、Gamepad API、Pointer Events、DeviceOrientation、localStorage、Service Worker |

メニューとHUDはHTML/CSSで作り、3D画面（canvas）の上に重ねる。文字の表示や画面サイズへの対応がcanvasで作るより簡単なためだ。

## 2. 画面構成と遷移

MVPの画面は10個。基本の流れは「起動 → タイトル → 試合設定 → 試合 → リザルト → 試合設定」で、試合を短い間隔で何度も繰り返せるようにする。

| 画面 | 内容 | 主な遷移先 |
| --- | --- | --- |
| 起動 | 「タップしてスタート」。ここで音声を有効化し、最小限の素材を読み込む | タイトル |
| タイトル | ロゴ、タイトルBGM、「いざ、参る！」ボタン | メインメニュー |
| メインメニュー | 色取り合戦、修行場、設定、クレジット | 試合設定、修行場、設定 |
| 試合設定 | ステージ、武器、CPUの難易度、試合時間を選ぶ | ロード |
| ロード | ステージと音声の読み込み。操作のヒントを表示 | 試合 |
| 試合 | 3D画面とHUD | ポーズ、リザルト |
| ポーズ | 再開、設定、試合をやめる（試合は停止する） | 試合、設定、メインメニュー |
| リザルト | 塗り比率バーの演出、勝敗、個人成績 | 試合設定（もう一戦）、メインメニュー |
| 修行場 | 的当てと試し撃ち、操作チュートリアル | メインメニュー |
| 設定 | 音量、感度、ボタン配置、ジャイロ、画質、色覚サポート | 呼び出し元の画面 |

- 縦画面のときは、どの画面でも「横向きにしてください」の表示を上に重ねる
- 試合中にタブを切り替えたりアプリから離れたりしたら、自動でポーズにする（Page Visibility API）
- ゲームパッドが切断されたら自動でポーズにし、再接続を待つ

## 3. ゲームループと試合の流れ

1フレームの中で、ゲームの更新を固定間隔（1/60秒）で必要な回数だけ回し、最後に1回描画する。処理落ちしたときの更新は1フレームあたり最大5回までにとどめ、それ以上はゲームを遅らせて止まらないようにする。

**1回の更新の処理順**

1. 入力の取得（全デバイスからアクションへ変換）
2. CPUの意思決定（0.25秒ごと。毎回は判断しない）
3. キャラの移動と当たり判定
4. 武器の発射、弾の移動、着弾
5. 着弾した位置への塗り（GPUのテクスチャとCPUのグリッドの両方）
6. ダメージ、撃破、復帰の判定
7. 試合の時間と奥義ゲージの更新
8. 音と演出のイベント発行（ここではイベントを溜めるだけで、再生はまとめて行う）

更新が終わったら、キャラの位置を前回と今回の間で補間して描画し、最後にHUDを更新する。

**試合の流れ**

1. **開始前**（3秒）：カメラがステージを見渡し、「いざ、参る！」のコール。入力は受け付けない
2. **試合中**（3分）：通常BGM。塗り比率は試合中は表示せず、最後まで勝敗をわからなくして盛り上げる
3. **残り1分**：「時は来た！」のコールと同時にBGMを切迫系へ切り替える
4. **残り10秒**：画面中央にカウントダウン、1秒ごとにカウント音
5. **終了**：ホイッスル、全員の操作を止める。0.5秒後に塗り面積を確定する
6. **判定演出**：塗り比率バーが左右から伸びる演出、勝鬨または敗北のジングル
7. **リザルト**：個人成績の表示、「もう一戦」で試合設定へ

## 4. サブシステム設計

ゲームの手触りを決めるのは「塗り」と「キャラの移動」の2つ。ここはプロトタイプで最初に作り、調整に一番時間をかける。

### 4.1 入力（InputManager）

- デバイスごとのアダプター（キーボード・マウス／ゲームパッド／タッチ／ジャイロ）が、共通のアクション状態に書き込む
- アクションは「移動（2軸）」「視点（2軸）」「射撃」「ジャンプ」「染遁」「彩煙玉」「奥義」「ポーズ」の8種類
- ゲームパッドは毎フレーム状態を読み取り、スティックにデッドゾーンを設ける
- 最後に操作したデバイスに合わせて、画面のボタン表示（キー名・パッドのボタン名・タッチボタンの表示有無）を切り替える
- ジャイロは視点入力に加算する。iOSでは設定画面でONにしたときに許可を求める

### 4.2 塗り（PaintSystem）

- ステージの塗れる面をすべて1枚のテクスチャ（アトラス）に割り当てる。解像度は画質設定で変える
- 着弾したら、スプラット（飛び散り形状）の画像をGPUでアトラスに描き込む。テクスチャの各ピクセルには「どのチームの色か」を持たせ、表示色はシェーダーで決める。色覚サポートはここで配色を差し替えるだけで済む
- 同じスプラットを、CPU側の低解像度グリッド（チームIDの配列）にも書き込む。足元の色の判定、面積の集計、CPUの判断はこのグリッドだけを使う
- 面積の集計は0.5秒ごとに行う。チームごとのセル数を差分で更新し、全セルを毎回数え直さない

### 4.3 キャラと物理（Player / Physics）

- キャラはカプセル形の当たり判定で、ステージの簡易コリジョン形状に対して移動させる
- 状態は「構え」「染遁」「空中」「やられ」「復帰待ち」の5つで、状態遷移として管理する
- 足元の色によって、移動速度・ペンキ回復・ダメージを切り替える（自分の色／敵の色／塗られていない）
- 染遁中に自分の色の壁へ向かって進むと、壁を駆け上がる
- カメラはキャラの後方に置き、壁にめり込まないよう手前に寄せる

### 4.4 武器（Weapon）

- 武器の性能はJSONの定義から読み込み、弾の種類で処理を分ける
- 彩手裏剣：放物線を描く弾。着弾点と飛んだ道筋に小さく塗る
- 大筆：前方の帯状の範囲を塗り続け、触れた敵にダメージ。振り抜きでまとめて塗る
- 長吹き矢：溜め時間に応じて射程が伸びる直線の即着弾。線の上をまっすぐ塗る
- 彩煙玉：跳ねる投擲物。一定時間後に破裂して円形に塗る
- 奥義・百花繚乱：塗った量でゲージが溜まる。発動中は射撃速度と塗りの大きさを上げ、専用BGMに切り替える
- 弾と演出用の粒子はあらかじめ作っておいて使い回し（オブジェクトプール）、処理落ちの原因になるメモリの確保と解放を避ける

### 4.5 CPU（AI）

- 0.25秒ごとに「塗る」「敵を追う」「味方を援護する」「下がって回復する」の候補を点数化し、一番高い行動を選ぶ
- 移動経路は、ステージデータに手で置いた通り道（ウェイポイント）のつながりから探す。初版では自動生成のナビメッシュは使わない
- 難易度は「反応の速さ」「狙いのぶれ」「判断の間隔」の3つの数値で変える

### 4.6 サウンド（AudioManager）

- 音量を「BGM」「効果音」「ボイス（掛け声）」の3系統に分け、それぞれ設定で調整できる
- BGMの切り替えはクロスフェード（約1秒）で行う
- 効果音は同時発音数の上限を超えたら優先度の低い音から止める。自分の音と近くの音を優先し、遠くの音は距離で小さくして左右に振る
- 塗りの音は、そのフレームで塗った量に応じて音量と音程を上げる

### 4.7 表示とHUD（UI）

- 試合中のHUD：残り時間、ペンキ瓢箪の残量、奥義ゲージ、撃破ログ、味方と敵の生存状況
- 演出：撃破時のヒットストップ（約0.05秒の停止）、画面揺れ、煙と木の葉の粒子
- タッチボタンは左右の親指が届く位置に置き、配置と大きさを設定で変えられるようにする

## 5. データ設計

データは「ゲームに同梱するマスターデータ（JSON）」と「プレイヤーの端末に保存する設定と記録（localStorage）」の2種類だけ。サーバーとデータベースは持たない。

**マスターデータ（ビルドに同梱、読み取り専用）**

| ファイル | 主な項目 |
| --- | --- |
| weapons.json | ID、表示名、種別、ダメージ、射程、連射間隔、塗りの大きさ、ペンキ消費量、奥義ゲージの溜まりやすさ |
| subs.json | ID、表示名、ペンキ消費量、破裂までの時間、塗り半径、ダメージ |
| specials.json | ID、表示名、必要ゲージ量、効果時間、強化倍率、専用BGMのID |
| stages/〈ID〉.json | 3Dモデルのファイル、コリジョン形状、塗れる面の一覧、出撃地点、ウェイポイント、使用BGM |
| ai.json | 難易度ごとの反応の速さ、狙いのぶれ、判断の間隔 |
| audio.json | 音のID、ファイル、系統（BGM／効果音／ボイス）、既定の音量、優先度、ループの有無 |
| text.json | 画面に出す文言（武器名、ボタン名、掛け声の字幕など） |

**保存データ（localStorage）**

| 項目 | 内容 |
| --- | --- |
| 保存キー | `paintrush.save`（中身にバージョン番号を持たせる） |
| 設定 | 3系統の音量、視点感度、上下反転、ジャイロのON/OFF、画質、色覚サポート、キー割り当て、タッチボタン配置 |
| 記録 | 試合数、勝利数、武器ごとの使用回数、1試合の最高塗りポイント |
| 前回の選択 | 最後に選んだ武器、ステージ、難易度 |

- バージョン番号が古い保存データは、読み込み時に新しい形式へ変換する
- 保存データが壊れていたり読めなかったりしたら、既定値で起動する（プライベートブラウズでは保存できないことがある）

## 6. ディレクトリ構成・ビルド・デプロイ

mainブランチにpushすると、GitHub Actionsがビルドし、GitHub Pagesへ自動で公開する。手作業でのアップロードはしない。

```
paint-rush/
├─ src/
│  ├─ main.ts            起動処理
│  ├─ engine/            ループ、描画、入力、音声、読み込み、保存
│  ├─ game/              試合、キャラ、武器、塗り、CPU、物理
│  ├─ ui/                各画面、HUD、タッチボタン
│  └─ data/              マスターデータ（JSON）
├─ public/
│  ├─ assets/models/     3Dモデル（glTF / .glb）
│  ├─ assets/textures/   テクスチャ（KTX2）
│  ├─ assets/audio/      音声（.ogg と .m4a）
│  └─ manifest.webmanifest
├─ .github/workflows/deploy.yml
├─ CREDITS.md            素材の出典とライセンス
└─ LICENSE               コードのライセンス
```

| 項目 | 方式 |
| --- | --- |
| 言語・ビルド | TypeScript（strictモード）＋ Vite |
| コード品質 | ESLint と Prettier。プルリクエストごとにActionsで型チェックとビルドを確認 |
| 3Dモデル | glTF（.glb）。頂点データはmeshoptで圧縮する |
| テクスチャ | KTX2（Basis圧縮）。スマホのGPUメモリを節約する |
| 音声 | Opus（.ogg）と AAC（.m4a）を両方用意し、端末が再生できる方を読む |
| PWA | vite-plugin-pwa でService Workerとmanifestを生成。2回目以降はオフラインでも起動する |
| 公開 | GitHub Actions の Pages デプロイ。公開URLのサブパス（/リポジトリ名/）をViteのbase設定に合わせる |

読み込みは2段階に分ける。起動時はタイトルとメニューに必要な最小限だけを読み、ステージと試合用の音声は試合設定の後に読む。

## 7. 性能・端末対応の方針と未決事項

画質は「低・中・高」の3段階とし、試合開始から数秒のフレームレートを測って自動で選ぶ。設定画面で手動に切り替えることもできる。

| 項目 | 低 | 中 | 高 |
| --- | --- | --- | --- |
| 描画解像度 | 画面の約0.6倍 | 画面の約0.8倍 | 等倍 |
| 塗りテクスチャの解像度 | 512px | 1024px | 2048px |
| 影 | なし | キャラのみ | ステージも含む |
| 粒子の上限数 | 少 | 中 | 多 |
| 想定端末 | スマホ中位機 | 新しめのスマホ、iPad | PC、Mac |

**端末ごとの対応**

- iOS・iPadOS：最初のタップで音声を有効化する。ホーム画面に追加すると全画面で遊べる。ジャイロは許可ダイアログを出す
- Android：機種の性能差が大きいため、画質の自動選択を必ず効かせる
- PC・Mac：マウスは画面クリックでカーソルを固定（Pointer Lock）し、Escで解除してポーズにする

**未決事項**

- [ ] 物理処理を自前の簡易判定にするか、Rapier（WASM）を使うか。プロトタイプで両方の手間を比べて決める
- [ ] 3Dモデル（彩忍、武器、ステージ）の制作手段：Blenderで自作、AI生成、フリー素材のどれにするか
- [ ] ステージの作り方：Blenderでモデルを作り、出撃地点やウェイポイントをオブジェクトの名前や独自のプロパティで埋め込む案が有力
- [ ] 動作確認に使う最低端末の決定（実機テスト用）
